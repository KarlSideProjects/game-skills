# Emulator and artifact provenance

A visual result is reproducible evidence only when tied to the exact input image, emulator build, machine profile, assets, and inputs. Save a compact JSON run manifest next to screenshots and traces. Include these fields where applicable:

- `source`: original CUE and every track path, source Track 1/Track 2 SHA-256, extraction manifest SHA-256, and hashes of each modified source file.
- `emulator`: core name/version, source commit, build configuration, executable path and executable SHA-256. Record the actual binary used; a source commit alone is insufficient.
- `machine`: Saturn/expansion profile, such as DRAM32M, cartridge profile and ID mode.
- `patch_inputs`: event/script SHA-256, translation cache or approved batch manifest SHA-256, character map SHA-256, FONT asset SHA-256 and manifest SHA-256, helper SHA-256, and any patch-plan SHA-256.
- `run`: starting state path and SHA-256 plus cartridge sidecar hash if used; frame count; input script and its SHA-256; save-state/checkpoint hashes; and whether runtime code overrides were enabled.
- `result`: output CUE/BIN track paths and SHA-256 values, combined disc SHA-256, screenshot/trace/dump paths and SHA-256 values, tested scene, visible text scope, and explicit PASS/FAIL/UNVERIFIED status.

## Release image and runtime proof gate

For an ISO patch, verify each compiled file as a whole, not only changed bytes: extract its declared LBA/size from the final MODE1/2352 Track 1 and require exact byte equality and SHA-256 equality with the compiled candidate. Preserve this identity in the patch manifest for every changed file (for example `/0.BIN`, `/1.BIN`, and `/FONT.BIN`). For the emulator's combined single-file BIN, hash the complete Track 1 prefix and complete Track 2 suffix separately; require the prefix hash to equal the final Track 1 hash and the suffix hash to equal the original audio Track 2 hash. Keep both exact track lengths and the generated CUE beside that combined image. The Vandal Hearts adapter's existing `verify_hud_trial_disc.py` and `prepare_yabause_cue.py` perform these checks as a two-step chain; do not replace them with a second generic verifier.

Every runtime assertion that maps code or data back to the ROM must state both the runtime load base and file offset, and must compare bytes at that exact location. If the memory dump stores words pair-swapped, normalize each 16-bit pair before comparing. Record the raw dump and normalization rule. Each run gets a new directory and its own manifest, core/executable SHA-256, source and combined-track hashes, machine/cart profile, input script hash, initial/save-state hashes, frame count, and runtime-override setting. A host-side override may demonstrate that a hook can render; it is diagnostic only and cannot establish that the final BIN/CUE contains or executes that behavior. Accept a ROM-backed visual PASS only from a run using the final image with runtime overrides off, exact image provenance, and target-pixel evidence.

Treat a save state and input script as one scenario identity. If navigation changes from a held/global button to a short edge plus direction presses, create a separate run manifest and input hash; do not join its frames, register trace, or screenshots to the earlier schedule even when the state file is shared. Record exact input event frame numbers and distinguish state-load frames from run-relative frames.

For Vandal Hearts movie hooks and generated SH-2 helpers, verify emitted words with the project's SH2Disasm against the source-bound module and include the runtime PC, module load base, and file offset. Check branch-delay slots and direct branch targets in the overwritten window. A zero cave or an interval with no instruction fetches in one scene does not prove that no data reader, loader copy, or other scene uses those bytes.

The Vandal Hearts English v1.4 dialogue proof provides a historical reference: source Track 1 SHA-256 `6bae252e67460fa7b616adb6d5da9c3a4a92589fa35742a8874b6628f02c2f07`; tested combined Track 1 SHA-256 `a743ab28475663369c609cc584e5fb1766a3342c67fb30320f6614ff86768d4c`; combined disc SHA-256 `e4031bdc2c85717d4f3812a1dc1b0c86d7c7935960a0439a588fe68242ee2e16`; font, event, and helper hashes are listed in `vandal-hearts-en-v1.4.md`. It ran 11,900 frames with DRAM32M, normal cart ID mode, and no runtime override. Those old hashes identify that test build, not a current emulator executable; future reruns must capture the actual emulator executable hash and current run manifest.

A screenshot without these inputs is an illustration, not a reproducible pass. Keep track 2 audio and its hash in the manifest even when only Track 1 changed. Never overwrite the source BIN/CUE; write a new image and verify sector integrity, extents, and preserved audio before launching it.

## Interactive GUI evidence

For the project's Vandal Hearts GTK runner, distinguish the default SHA-checked title-menu save-state session from `play_vandal_hearts.sh --cold`; the former is a quick interaction path, not a cold-boot result. Record the exact command and mode, selected CUE, package manifest, declared and independently verified track hashes, menu state and cart-sidecar hashes/profile, emulator executable hash, and whether runtime overrides were off. The current launcher compares the prepared-disc manifest's declared Track 1/Track 2 identities to the package manifest but does not recompute the combined BIN's bytes at launch. Independently validate packaged files and prepared combined track prefix/suffix before relying on those declarations.

Separate display initialization, framebuffer pixel identity, keyboard interaction, and audible output into distinct observations. A window or process existing is only initialization evidence. A screenshot or captured framebuffer establishes pixels for that frame; keyboard and sound require their own exercised observations. A project-provided `check_framebuffer.sh` may be a bounded regression from a fixed menu save state: pixel-for-pixel headless PPM, GUI PPM, and Cairo PNG agreement checks live dimensions/stride and color conversion only. It does not certify cold boot, sound, input, or game completion. Such checks should take their headless runner path from explicit CLI/configuration (for example `VH_HEADLESS`), not a machine-fixed `/tmp` path. Verify the runner is executable and built from the intended project before running. Do not describe framebuffer captures as desktop screenshots or hardware-console captures.
